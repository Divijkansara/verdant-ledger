Document 01 · UI/UX Design Specification

Verdant Ledger

Wireframes & screen specification

A web application that maintains an organisation's digital sustainability ledger. Activity across eight categories — electricity, water, waste, transportation, paper, procurement, recycling and renewable energy — is posted as dated entries, priced against published emission factors, and continuously rolled up into a carbon footprint, resource-consumption totals and a composite sustainability score.

Reading this document. Each screen is drawn as a low-fidelity wireframe: greyscale blocks, no colour, no final copy. That is deliberate — a wireframe specifies structure, hierarchy and behaviour. Numbered markers on each drawing correspond to the annotation table beneath it, which names the component, what it does, and the API endpoint that supplies its data.

Design principles applied

PrincipleHow it shows up in these screens
Visibility of system status
Nielsen #1		The Log Activity screen prices the entry live as the user types, before submitting. No one posts a number blind.
Recognition over recall
Nielsen #6		Activities are chosen from a labelled catalogue with units and factors shown — the user never has to remember that grid power is 0.716 kg/kWh.
Error prevention
Nielsen #5		Future dates and non-positive quantities are blocked in the form and again at the API. Destructive edits do not exist: entries are voided with a reason, never deleted.
Aggregation before detailDashboard opens with one score and four figures; the 300-row ledger is one tab away, not on the landing screen.
Progressive disclosureThe full 39-factor methodology lives on its own tab, reachable but never in the way.

Why the preview step exists. The preview endpoint runs the same calculation engine as the real posting, so the figure shown before submitting is exactly the figure that will be stored. This turns the riskiest moment in the app — committing a number to an auditable ledger — into a reversible, visible one.

There is no delete. The row survives for audit; only its contribution to the totals is removed. The API returns 405 Method Not Allowed for DELETE /api/entries/{id} — the constraint is enforced in the backend, not just hidden in the UI.

900–1179Container fluid. KPI grid stays 2 × 2; chart row stays two-up but narrows.

11 · Global states every screen must handle

StateTreatment
LoadingSkeleton blocks at the final dimensions, so nothing jumps when data arrives. Never a full-page spinner — the shell and tabs stay usable.
EmptyA new organisation has no entries. Charts are replaced by one card explaining what to do, with a button straight to Log Activity. Never an empty axis with no bars.
ErrorPanel-level, not page-level: if the insights call fails, the score and charts still render. Each failed panel offers its own retry.
Read-onlyViewer role: writing controls are hidden and the API refuses them with 403. Permission is enforced on the server; the UI only reflects it.
Offline / expired tokenA 401 on any call clears the session and routes to login with a "your session expired" message, preserving the intended destination.

12 · Accessibility checklist

RequirementImplementation
Colour is never the only signalEvery chart series is directly labelled; status chips carry text ("On track") as well as colour; voided rows are struck through, not just dimmed.
Contrast ≥ 4.5:1 for textBody and label colours checked against both the light and dark surfaces.
Keyboard operableTab order follows reading order; category tiles are an arrow-key radiogroup; dialogs trap focus and close on Escape.
Visible focusA 2 px outline on every interactive element — never outline:none without a replacement.
Semantic structureOne h1 per screen, real <table> markup for the ledger, role="tablist" with aria-selected on the nav.
Announced updatesForm errors and the post confirmation sit in aria-live regions so a screen reader hears them.
Reduced motionAll transitions disabled under prefers-reduced-motion.
